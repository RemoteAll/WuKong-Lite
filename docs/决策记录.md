## 第 31 轮 · 按 D123BBV（d12x）重打固件（2026-11-19）

**用户要求（原话）**：“帮我使用ziglang打包D123BBV这个型号的固件，上次你给我打包的那个烧写时提示型号不对”。

### 先定性：D123BBV 是什么

实测依据（不是猜）：
- `bsp/artinchip/sys/d12x/ram_param.c` 的 `PSRAM_TABLE_INFO` 里有 `/* D123BBV 8M */`
  → `{0x08, PSRAM_PARALLEL, 0x800000, {PSRAM_FUSE_APS3208K, 0x80c980c9}}`；
  同表还有 `D123BAV 4M` / `D123BCV 16M` / `D123BDV 32M`。
- `bsp/artinchip/sys/d13x/ram_param.c` 里 grep `D123` **零命中**。

结论：**D123BBV 是 d12x 系列芯片（8 MiB 并行 PSRAM）**；上次交付的是 `d13x_demo88-nor_zig_v1.0.0.img`，
芯片系列不同 → 烧写工具报“型号不对”是必然的（不是固件坏了）。

### 交付

| 项 | 值 |
|----|----|
| 文件 | `artifacts/firmware-d12x/d12x_demo68-nor_v1.0.0.img` |
| 大小 | 9,419,264 B |
| SHA256 | `A4C2818CB09F9EBC2A38956082FBBC9E162524DE82C2925EF11D6F98E7454A05` |
| AIC.FW 头 | `platform=d12x`、`product=demo68-nor`、`media=spi-nor`、`version=1.0.0` |
| 内容 | 官方 bootloader + RT-Thread + LVGL V9 `demo_hub`（480×272 屏 + i2c0 触摸 RST=PA.10/INT=PA.11） |

烧写（UART）：
`wk\image\tools\upgcmd\upgcmd.exe -i <img> -u COM5 -p -v`（先跑 `tools\fetch-upgcmd-deps.ps1` 补 3 个 DLL）。

### 三个实测发现（都固化进脚本与注释）

1. **参考 SDK 的 d12x 方案自身不一致**：链接产物是 `<soc>.elf`（实测 `d13x.elf`），
   而 `target/d12x/*/pack/image_cfg.json` 的 `elf2itb` 段写 `d12x.elf` →
   SCons 的 POST_ACTION 跑 `mk_image.py` 必然报 `File d12x.elf is not exist`。
   `.config` 里是 `CONFIG_AIC_CHIP_D12X=y`、`rtconfig.h` 里 `AIC_CHIP_D12X` → **编译宏正确**，
   只是文件名对不上；复制 ELF 即可（`d13x.elf` 与 `d12x.elf` 内容逐字节相同，已用 SHA256 校验）。
2. **`build/luban-lite` 副本此前被 `tools/attach-zig-sdk.ps1` 注入过**：`main.c` 里有 `wk_sdk_demo();`、
   `application/rt-thread/helloworld/zig_sdk/SConscript` 存在 → 产出的会是 Zig 版 LVGL UI。
   这轮**撤销了注入**（删 `zig_sdk/`、去掉调用行），交付的是官方 `demo_hub`，
   避免 Zig SDK 在新芯片上未经验证。要 Zig 版：`-WithZig`。
3. **`mk_image.py` 会把构建时间写进 `image.info`** → 同一份输入两次打包 SHA256 不同（本次
   `D58956A2…` → `A4C2818C…`，大小不变）。因此**哈希只对“这一次产物”有效**，不能当构建指纹。

### 新增：`tools/build-d12x-firmware.ps1`（一键、可复现）

## 第 32 轮 · 全链路 Zig 打包：补 `elf2itb`，交付固件不再经过厂商 Python（2026-11-19）

用户原话：**「是用ziglang的来打包的吗？我要的是用我们自己ziglang生成的固件哦」**

### 背景

第 31 轮交付的 `.img` 芯片型号正确，但**打包这一步走的是参考 SDK 的 `mk_image.py`**（厂商 Python），
与「用我们自己的 Zig 工具链产出固件」的目标不符。

### 缺口定位

`image_cfg.json` 的 `pre-process` 共 **7 类段**，此前我们实现了 6 类，独缺 **`elf2itb`**
（ELF → ITS → FIT 一步到位），而 d12x 的 OS 镜像（`d12x_os.itb`）正是走这一段。

### 实现（`src/tools/preproc.zig::runElf2itb`）

- **ELF → ITS**：复用 `elf2aic.itsSegments`，`description` 固定 `"Luban-lite firmware"`（与参考
  `elf2image.elf2its` 一致）；ITS 文本按**平台换行**写出（参考在 Windows 上写 CRLF）
- `platformNewline()` / `toPlatformNewlines()` 由 `partcheck.zig` 提到 `bsp/common/utils.zig` 共用
- **ITS → FIT**：`buildFdtExternal`，`block_align = 0x800`，数据落 `<name>_seg0.bin`（目录布局与参考相同）
- `signature` / `encryption` 字段**显式报错**（不静默产出未签名镜像）

### 对拍（新脚本 `tools/checks/check_elf2itb.py`，已进回归）

用 d12x 真实构建件对比 `mk_image.py -p` 与 `wk image preproc`：

| 产物 | 结果 |
|------|------|
| `d12x_os.its` | ✅ 逐字节一致（506 B）|
| `seg0.bin` | ✅ 逐字节一致（1,615,984 B）|
| `d12x_os.itb` | ✅ 归一时间戳后逐字节一致（1,619,968 B）|

> 参考用 `int(time.time())` 写 FIT 根 `timestamp`，无法固定，故脚本先把两侧 timestamp 归一再比。

### 全链路 Zig 打包实测

`tools/build-d12x-firmware.ps1` 默认已改走 `wk image preproc` + `wk image pack`
（`-UseReferencePacker` 才切回厂商 Python），并新增 `-timestamp` 便于复现：


## 第 33 轮 · 烧写失败定位：与"能升级的固件"逐组件对比（2026-11-19）

用户原话：**「固件还是失败」**（附图：AiBurn v2.1.1，进度 3%、速率 10.7 KB/s、用时 1:13、结果 FAIL、启动阶段仍为 BROM），
随后提供对照物：**「这个固件是目前能升级成功的固件，你要帮我对比一下」**
（`d12x_demo68-nor_v1.0.0.img`，6,607,360 B，SHA256 `383ABD06…3DB61D`）。

### 对比结论（全部为实测数据）

| 组件 | 能升级的对照固件 | 我方 | 判定 |
|------|-----------------|------|------|
| `info.bin` | 2,048 B | 2,048 B | **只差 2 字节**（0x0159-0x015A 构建时间戳）→ 分区表/介质/版本完全一致 |
| `env.bin` ×2 | CRC `0xCE19208A` | CRC `0xCE19208A` | **完全相同** |
| `uartupg-psram-init.aic` | 36,112 B | **34,576 B** | 差 1,536 B；内嵌 pbp 不是同一份 |
| `bootloader.aic` | 255,504 B | **260,880 B** | 差 5,376 B；不同 SDK 版本产物 |
| `d12x_os.itb` | 1,128,448 B | 1,619,968 B | 我方 app 更大（配置更多） |
| `rodata.fatfs` | 4,648,960 B | 6,959,104 B | 我方资源更多 |
| `data.lfs` | 266,240 B | 266,240 B | 大小同、内容不同（可写分区，不影响烧写） |

**失败点定位**：进度 3% ≈ 9.4 MB×3% ≈ 282 KB，而 `psram-init + bootloader` 合计
我方 295,456 B / 对照 291,616 B —— **失败正好发生在"传完 spl、等 spl 接管"那一刻**，
且 AiBurn 此时仍显示 `BROM`，说明 spl 没能跑起来。

**PSRAM 型号表差异（psram-init 内按型号 ID 计数）**：我方缺 `W957D6NKR`(0→3)、`W956D8NKR`(0→3)，
`APS6408L` 少 1 处；**D123BBV 用的 APS3208K 两边都是 13 处**，所以型号表不是直接原因，
但两份内嵌 `d12x.pbp` 版本不同。

**结论**：分区/介质/版本侧没有问题，差异集中在两个 BROM 阶段二进制上；
我方 bootloader.bin（223,664 B）与当前官方 SDK `target/d12x/demo68-nor/pack/bootloader.bin` 同尺寸，
对照固件的约 218,288 B —— **最可能是新版 SDK 的 bootloader 与这块板子（或其配对的 psram-init）不匹配**。
